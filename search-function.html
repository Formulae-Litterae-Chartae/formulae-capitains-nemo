Search function

How a Search Request Is Processed

This page follows three requests through r_results() (route /search/results) and advanced_query_index().

From the search form to the URL

The simple-search form (simple-search-form) submits by GET to search.r_simple_search (/search/simple), not to the results page. The form is created for every request in before_request (g.search_form = SearchForm()). r_simple_search converts the form data and redirects to /search/results:

Form field

Conversion

q_1

Lowercased.

simple_search_id

Renamed to search_id.

search_field

Renamed to search_field_1 (default text).

lemma_search

Removed from the data. If it is y, True or True (boolean), search_field_1 is set to lemmas. The parameter itself does not appear in the redirected URL.

corpus

List joined with +. url_for encodes the + as %2B.

Special cases:

  • If the form is invalid because of q_1, a message is flashed (“the simple search only works with one search word”) and an empty 204 response is returned, so the page does not change.

  • If no corpus is selected, a message is flashed and the user is redirected with corpus=formulae+chartae.

  • The redirect always uses source=simple and sort=urn. All remaining form fields are passed on as URL parameters.

Processing steps

1. Parameter check

If source is missing, the user is redirected to InstanceNemo.r_index.

2. Resolving the corpus

The corpus value is split on + and then on spaces. The result decides which collections are listed:

corpus

Collections in corps

contains elexicon

elexicon only

all, formulae+chartae, empty, form_lit_chart

formulae_collection plus (sorted) other_collection

formulae

formulae_collection

chartae

other_collection (sorted)

anything else

the given IDs, used as they are

The members of each group are defined in the Capitains metadata files under data/. For corpus=formulae, the members of data/formulae_collection/__capitains__.xml are used:

<collection identifier="urn:cts:formulae:andecavensis"
            path="../andecavensis/__capitains__.xml"/>
<collection identifier="urn:cts:formulae:auvergne"
            path="../auvergne/__capitains__.xml"/>
<!-- ... -->

The last segment of each URN (andecavensis, auvergne, …) becomes an entry in corps.

Every ID in corps is mapped through CORP_MAP['form_lit_chart-<id>'] to build g.corpora. If an ID is missing, a KeyError is logged. Collections listed in ES_EXCLUDE_COLLECTIONS are then dropped as a temporary workaround; if that setting is empty, the error is re-raised.

Note

These files identify collections, not individual formulae. Individual texts are defined in each sub-collection’s own __capitains__.xml.

Important

The expanded list corps is used only for g.corpora and the stored search arguments. The search itself receives the unexpanded corpus list (for example ['formulae']) and passes it directly as the index argument of the Elasticsearch calls in advanced_query_index(). If corpus is empty or all, it is replaced by ['form_lit_chart']. The values formulae, chartae and form_lit_chart therefore have to exist as Elasticsearch aliases.

Note

formulae, chartae and form_lit_chart are Elasticsearch aliases created by rebuild_elasticsearch_from_xml.py. The script:

  • builds coll_type.json by walking data/display_formulae/__capitains__.xml (every text group found is mapped to formulae),

  • indexes each text into a versioned index form_lit_chart-<id>_vN,

  • puts three aliases on it: <id>, the type from coll_type (formulae, elexicon or, as a fallback, chartae) and form_lit_chart.

A collection missing from coll_type silently becomes part of chartae. The index must be rebuilt after changes to the Capitains files. CORP_MAP and corpus_agg only affect the displayed corpus list and the aggregation buckets, not which indices are searched.

Note

The default for regex_search is the boolean False, whereas build_search_args produces the strings 'True' and 'False' and advanced_query_index compares against these strings. See the wildcard warning in example 2.

4. Running the search

The remaining arguments (dates, forgeries, bool_operator, …) and query_dict are passed to advanced_query_index. Date fields default to 0, per_page is fixed at 10000, forgeries defaults to include and bool_operator to must. The function returns the hits, the total count, the aggregations and the previous-search information.

For source=simple, a regest clause is added to every query. The query terms must match either the selected search field or the regest of a text, so simple searches also find texts through their summaries. The regest field is highlighted as well.

If several queries are present (for example q_1 and a second query created from regest_q), each is run separately. The results are then combined according to bool_operator: must keeps the hits shared by all queries, must_not removes the hits of later queries from the first, and should keeps all hits.

5. Storing the search for later pages

Unless old_search=True, the request arguments are saved in g.previous_search_args (corpus is replaced by the expanded list of collection IDs) and the aggregations in g.previous_aggregations.

6. Lemma lookup

For every query whose search_field is not lemmas, each token is looked up in inflected_to_lemma_mapping. Tokens containing ? or * are first expanded against the highlighted words. A query appears in searched_lems only if all of its tokens have at least one lemma; max_cols is the largest token count among them.

7. Rendering

The template search::search.html is rendered with the hits, total, aggregations, searched_lems and max_cols.

r_results and advanced_query_index never read q or lemma_search directly. build_search_args translates them (see step 3). URLs with q and lemma_search are therefore accepted only as a convenience for hand-made or older links.

The tooltip of the checkbox (id="simple-lemma-checkbox") states that lemma search is only possible for Latin formulae texts.

Differences from example 1

Corpus. formulae+chartae is split on + into ['formulae', 'chartae']. This exact list is one of the “all collections” cases, so corps contains the members of formulae_collection followed by the sorted members of other_collection. The search itself receives the unexpanded list and passes it as index=['formulae', 'chartae'] to Elasticsearch, which searches both aliases.

Warning

The comparison is order-sensitive. chartae+formulae does not match the special case and is treated as a list of collection IDs, which do not exist in CORP_MAP.

No search ID. search_id is empty, so no search_progress_... ID is used.

Query. Because search_field is lemmas, advanced_query_index behaves differently:

  • fuzziness is forced to '0'.

  • The u/v, i/j and w/uu normalisation applied to text searches is skipped.

  • If the searched lemma is a key of nemo_app.lem_to_lem_mapping, each related lemma is added as an extra clause (see example 3 and Lemma mapping files).

  • The lemmas field is added to the highlighted fields.

  • ? and * are meant to be rejected with a flash message and an empty result, unless regex_search is 'True'.

Warning

The wildcard rejection only works if regex_search is the string 'False'. build_search_args sets that string only when a regex_search parameter is present in the request. Otherwise r_results uses the boolean False, the comparison fails, and wildcards on lemmas are processed as ordinary wildcard (regexp) queries instead of being rejected. [TO BE VERIFIED: test with q=advoc*&lemma_search=True.]

Lemma lookup (step 6) is skipped for queries on lemmas, so searched_lems stays empty and max_cols is 0. The template therefore shows no inflected-form-to-lemma columns.

Highlighting. For every search that has a query, lem_highlight_to_text combines the highlighted fields and returns the text the user sees. For lemma searches, the highlights in lemmas are transferred to the text this way.

Example 3: a result that does not contain the searched word

https://werkstatt.formulae.uni-hamburg.de/search/results
    ?source=simple
    &corpus=formulae%2Bchartae
    &sort=urn
    &q=vicarius
    &lemma_search=True

This URL is built like example 2 (see there for the parameters), only with q=vicarius. It illustrates a case that can look like an error: the results include Bourges C 13 (urn:cts:formulae:bourges.form_c_013.lat001), although the text never contains the word vicarius.

Relevant content

Why the text is still found

  1. build_search_args turns q and lemma_search=True into q_1=vicarius and search_field_1=lemmas (see step 3).

  2. In advanced_query_index, the searched term is looked up in nemo_app.lem_to_lem_mapping, which is loaded from lem_to_lem.json (see Lemma mapping files). For vicarius the file contains:

    "vicarius": [
    "vigerius",
    "vicaria"
],

  3. One exact-match clause is created for vicarius itself and one for each related lemma, that is vigerius and vicaria. A text matches if it contains any of them. Because fuzziness is forced to 0 for lemma searches, each clause is an exact match.

  4. Bourges C 13 contains vicaria in its lemmas field, so it matches the third clause.

The mapping is applied to the searched term only, and only if that term is a key of lem_to_lem_mapping.

Note

The regest clause that is added for source=simple is not the reason for this hit. It uses the searched word as typed and does not apply the mapping, and the regest of Bourges C 13 does not contain vicarius.

Note

The mapping is directional by design (see Lemma mapping files). Its keys are variant lemmas, and its values are the primary lemmas that the annotators chose for the texts. vicaria is a primary lemma and has no key of its own in lem_to_lem.json. A search for vicaria therefore finds only texts whose lemmas field contains vicaria, whereas a search for vicarius finds texts containing vicarius, vigerius or vicaria. The results depend on which variant the user types.

What the user sees

The highlights are made in lemmas, and lem_highlight_to_text transfers them to the inflected text. The user should therefore see the spellings vigarias and vigaria highlighted, even though neither looks like vicarius. [TO BE VERIFIED in the result page.]

Finding out why a text was returned

  1. Open the text’s Elasticsearch document and check the field that was searched (lemmas for a lemma search, text otherwise).

  2. Look up the searched term in lem_to_lem.json. Every lemma listed there is searched as well.

  3. To find the annotation behind an entry, search the Pyrrha TSV files for the variant, for example grep -i vicarius ~/git/Lemmatization/pyrrha_output/*.tsv.

  4. If the cause is still unclear, inspect the request bodies built in advanced_query_index (the list searched_templates) and the highlight part of the hit.

Lemma mapping: lem_to_lem.json

Purpose

lem_to_lem.json is loaded as nemo_app.lem_to_lem_mapping [TO BE COMPLETED: where and when it is loaded]. advanced_query_index uses it for lemma searches to add related lemmas to the query (see example 3). The file is generated from the Pyrrha lemmatisation output, so corrections belong in the annotated TSV files, after which the file is regenerated.

Structure

{
    "vicarius": [
        "vigerius",
        "vicaria"
    ]
}

  • Key: a variant lemma (lowercase) that is not the primary lemma of an annotation.

  • Value: a list of the primary lemmas that the key was annotated with.

  • The keys are sorted alphabetically. The order of the values is arbitrary, because the script builds them from a set.

  • The primary lemma of an annotation does not get a key from that annotation. A lemma has a key only if it also occurs as a variant in some other annotation. This is why vicaria has no entry.

How the file is created

The script create_lem_to_lem_json.py (in corpus_transformation_scripts/lemmatization) reads the output files of Pyrrha. These are TSV files with the columns form, lemma, POS and morph. A line starting with ** marks the start of a new text. For every other line the script:

  1. lowercases the line and removes $,

  2. skips tokens that contain no word character (punctuation),

  3. splits the lemma column into a primary lemma and variants according to the notation below,

  4. adds variant -> primary lemma to the mapping for every variant that differs from the primary lemma.

Effect on the search

  • The mapping is applied when a query is built, not when texts are indexed. A new lem_to_lem.json therefore changes the results without a re-index, as soon as the application has loaded it. [TO BE COMPLETED: reload or restart procedure.]

  • The lemmatized field in the index is not produced by this script. If the primary lemma of a token is changed in the annotations, the texts have to be exported and indexed again (see rebuild_elasticsearch_from_xml.py).

  • Searching for a variant finds texts with the variant itself and with all its primary lemmas. Searching for a primary lemma finds only that lemma.

Source data: the Pyrrha output

The script reads TSV files exported from Pyrrha. Each file has the columns form, lemma, POS and morph.

  • The first line of every file (the header) is skipped.

  • A line that starts with ** marks the start of a new text. The name after the asterisks is used for the per-text files in results/.

  • Every other line is one token with its annotation.

What the script does

For every token line the script:

  1. keeps the original lemma column (case and $ unchanged) as the full lemma,

  2. lowercases the line, removes $ and skips punctuation,

  3. determines the primary lemma and the variants (see the notation above),

  4. adds variant -> primary lemma to lem_to_lem_mapping,

  5. adds inflected form -> primary lemma to inflected_to_lem_mapping,

  6. adds inflected form -> full lemma to inflected_to_full_lem_mapping, and to the formulae or charters variant of it, depending on whether the path of the TSV file contains formeln,

  7. adds the lemmas to the set all_lems, except those that contain ! or ? and the German placeholder lemmas (personenname, ortsname, volksstamm, monatsname, tagesbezeichnung, platzhalter).

At the end all sets are converted to lists and written as JSON with sorted keys, tab indentation and unescaped non-ASCII characters. Only the keys are sorted. The order inside the lists comes from sets and is therefore arbitrary and can change between runs.

The three files in detail

lem_to_lem.json

{
    "vicarius": [
        "vigerius",
        "vicaria"
    ]
}

  • Key: a variant lemma (lowercase).

  • Value: the primary lemmas that this variant was annotated with.

  • Direction: the mapping goes from variant to primary lemma only. A primary lemma has a key only if it also occurs as a variant in another annotation. vicaria is a primary lemma and has no key, so a lemma search for vicaria finds only vicaria, whereas a search for vicarius finds vicarius, vigerius and vicaria.

  • No filtering: the !, ? and placeholder filters of lemma_list.json do not apply, so such lemmas can appear here.

Use in the search. nemo_app.lem_to_lem_mapping is read in advanced_query_index:

  • For a lemma search, the searched term is looked up. If it is a key, one exact-match clause is added for the term and one for each listed lemma (see example 3).

  • For a proper-name search, lem_to_lem_mapping[term] is read without a default, so a name that is not a key may raise a KeyError. [TO BE VERIFIED: depends on how the mapping is loaded.]

inflected_to_lem.json

{
    "vicaria": [
        "vicarius",
        "vicaria"
    ]
}

  • Key: an inflected form as it occurs in the tokens (lowercase).

  • Value: the lemma annotations that this form received in the Pyrrha files. According to the script, these are the full lemma columns, taken before lowercasing and before $ is removed.

  • The example says that the form vicaria was annotated as vicarius in some places and as vicaria in others. This inconsistency is probably why lem_to_lem.json contains vicarius -> vicaria.

Loading. make_inflected_to_lem_mapping reads every file listed in the configuration setting INFLECTED_LEM_JSONS (currently .../inflected_to_lem.json) and merges them into one dictionary inflected_to_lemma_mapping. For a form that occurs in several files, the lemma lists are combined as a set, which removes duplicates and loses the order. An invalid JSON file is skipped with a logged warning. A missing file raises FileNotFoundError.

Use in the search. In r_results (step 6), each token of a text search is looked up in this mapping to fill the lemma columns of the result page. The mapping does not change which texts are found. The lookup uses the typed token as the key, which works because q_1 is lowercased earlier.

lemma_list.json

A sorted JSON list of all lemmas found in the input: all primary lemmas and all variant lemmas.

  • Lemmas containing ! or ? are left out.

  • The German placeholder lemmas are left out (see above).

  • In the a-b+c notation the primary lemma a is not added by itself. It appears in the list only if it occurs elsewhere.

Updating the files

  1. Correct the annotations in the Pyrrha output (the TSV files). Do not edit the generated JSON files by hand, because the next run overwrites them.

  2. Run the script (see above) and write the files to the destination folder.

  3. Copy lem_to_lem.json, inflected_to_lem.json and lemma_list.json to the place the application reads them from (formulae-corpora). [TO BE VERIFIED: copy procedure and whether the application must be restarted.]

  4. If the primary lemma of a token changed, the texts must be exported and indexed again, because the lemmatized field in Elasticsearch is not produced by this script (see rebuild_elasticsearch_from_xml.py).

Finding the annotation behind an entry

To see why lem_to_lem.json contains an entry, search the Pyrrha files for the variant:

grep -i vicarius ~/git/Lemmatization/pyrrha_output/*.tsv

The matching lines show the annotation (lemma column) that created the entry, for example a primary lemma followed by /vicarius.
